# 参照層（広報の号ページ）要約契約

Step B の抽出物を読み、追跡ファイル `src/content/posts` ではなく **`src/content/kouhou/<muniId>__<yyyy-mm>.md`** を書く。
外部 LLM API をリポジトリのスクリプトから呼ばない。エージェントが本契約に従い本文を書く（Step C と同じ運用モデル）。

```bash
npm run extract:kouhou
npm run generate:kouhou-pages            # frontmatter・出典シェルを用意し、チェックリストを表示
# → エージェントが本ファイルに従い本文・events を書く
# → npm run check:textlint / 必要なら個別修正
```

## 入力

- `data/kouhou/extracted/<muniId>/text.txt`（または `content.md`）と `meta.json`
- `sources/municipalities.yaml` の `listingUrl` / 名称
- 既存の `src/content/kouhou/<muniId>__<yyyy-mm>.md` があれば frontmatter を維持して本文を差し替える

文字化け・CID 化け・重複行・柱・ノンブルだらけの断片は**要約に使わない**。読めない箇所は省略する（「抽出失敗」と書かない）。

## 分量・粒度（必須）

参照層は検索の集客装置であり、**薄いダイジェストにしない**。読み物層のような話題の絞り込みはしない（POLICY §2.2）。

- **`## この号の案内`:** 「主要だけ」に絞らない。抽出文から読める周知・催し・募集・議会・制度・施設・報告を、分かる範囲でできるだけ列挙する（目安 **12〜30 件**。少ない号は無理に水増ししない）。各行は検索される語（制度名・施設名・手続き名・期限の種類）が先頭近くに来る短い句にする
- **`## 内容の要約`:** 話題を大きく束ねすぎない。広報のコーナー／記事単位で `###` を立てる（目安 **8〜20 本**。記事が少なければその分でよい）
- **各 `###`:** ですますの要約を **3〜8 文**目安。分かる範囲で **日付・場所・対象・申込・期限・料金・問合せ（部署＋固定電話）** を入れる。見出しまたは冒頭文に、自治体名と固有語（施設・制度・手続き）を含め、生活系の検索語に当たる形にする（例: 「秋田市の今冬の除排雪と高齢者支援」「潟上市の保育施設入所申込」）
- 私人欄・文字化け・柱だけの行は書かない。読めない箇所は省略し、読める記事で厚くする

## 出力（frontmatter）

```yaml
---
title: "{自治体名} 広報 {YYYY}年{M}月号"   # No. が分かれば末尾に（No.N）
description: "{自治体名}の広報{YYYY}年{M}月号の要約。{案内の先頭数件を読点でつなぐ}"
muniId: city-...
muniName: "…"
yearMonth: "YYYY-MM"
issueNo: ""          # 分かれば数字のみ
listingUrl: "…"
sourceUrl: "…"       # PDF または公式号ページ
sha256: "…"          # meta にあれば
generatedAt: "ISO-8601"
discoveredAt: "ISO-8601"  # 新規号ページの初回 scaffold 時のみ。既存値は必ず維持（消さない）
events: []           # 下記。無ければ空配列のまま
---
```

`description` は検索結果の抜粋向け。案内を書いたあと、先頭数件（目安 2〜4・全体でおおよそ 120〜155 字）を読点でつなぎ、定型の「公式広報〜の要約です。」だけで終わらせない。サイトの `<meta description>` は案内箇条書きからも自動生成されるが、frontmatter も揃えておく。

`discoveredAt` は「この自治体のこの月号を初めて参照層に載せた時刻」です。週刊号の「新着の広報」自動リストに使います。**既存ファイルを要約し直すときは必ず残す。** 無い号（このフィールド導入前のページ）は新着扱いしません。

### events

読者の役に立つ**これから／号内で案内されている催し・期限**だけを入れる。ノイズ行は入れない。分かる範囲で `when` / `what` / `where` / `contact` を埋める。

```yaml
events:
  - when: "2026年11月4日〜13日"   # 分かる範囲で具体的に
    what: "教育・保育施設等の入園申込"
    where: ""                      # 場所が広報にあれば
    contact: ""                    # 部署＋固定電話のみ。携帯は書かない
```

過去の報告記事だけの日付はイベントにしない。曖昧なら `events: []`。

## 本文構成

必ず入れる項目は次のとおりです。

1. 原本確認の `<aside class="info-note" role="note">`（定型文はシェルどおりでよい）
2. `## 出典`（公式案内リンク＋ PDF リンク）

内容があるときだけ入れる（**空なら章ごと省略**。失敗メッセージ・プレースホルダは禁止）。

- `## この号の案内` — 上記の分量どおりの箇条書き（読めない目次は作らない）
- `## 内容の要約` — 上記の粒度どおり `###` ＋ですます段落

禁止する文言・章は次のとおりです。

- 「機械抽出できませんでした」「原本の目次をご確認ください」など工程・失敗メタ
- 「抽出」「スキップ」「要確認」など運営向けメモ
- 空の `## この号の案内` / 空の `## 内容の要約`

## プライバシー（POLICY §6）

- 私人の氏名、070/080/090 は載せない
- 叙勲・出生・お悔やみ・戸籍の窓は載せない（章ごと省略）
- 公職者の氏名＋肩書は広報に出ている範囲で可
- 問い合わせは部署・団体＋公開固定電話のみ

## 文体

- ですます調
- 広報の丸写し禁止。意味の通る日本語に要約する
- textlint（ja-technical-writing）対象。句点・文長・半角カナに注意
- 画像は埋め込まない

## 完了条件

- [ ] 各対象ファイルで、案内または要約の少なくとも一方に読める内容がある（両方空は不可。読めない PDF のみ出典＋注記でも可だが、その場合は案内・要約章を付けない）
- [ ] 分量・粒度の目安を満たす（記事が極端に少ない号・読めない号は除く）
- [ ] 失敗・工程メタの文言がない
- [ ] `events` にゴミ行がない
- [ ] `npm run check:textlint` が通る（kouhou 含む）
- [ ] 人間がざっと確認してから commit
